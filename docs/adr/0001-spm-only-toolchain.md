# ADR 0001: SwiftPM only, no Xcode project

Date: 2026-09-18. Status: accepted.

## Context

The brief asks for an Xcode project generated by XcodeGen or Tuist (B-1), a String Catalog
(LOC-6) and XCTest style unit tests. The development machine has the Command Line Tools with the
macOS 27 SDK and no Xcode. Probing that toolchain showed:

- `swift build` works, Swift 6 language mode included.
- `@Observable`, `@Bindable`, `@Binding`, `@Environment`, `@FocusState`, `@Namespace`,
  `.glassEffect`, `NSGlassEffectView` and the `Settings` scene all compile.
- `@State` does not: from the macOS 27 SDK on it is a macro whose plugin (`SwiftUIMacros`) ships
  only with Xcode.
- `swift test` does not: neither XCTest nor the swift-testing macro plugin is in the Command Line
  Tools.
- `.xcstrings` catalogs are compiled by a tool that ships only with Xcode.

A sibling project, DevDeck, already ships signed and notarised releases from a SwiftPM package
with a hand-assembled bundle, and its release workflow is reused here.

## Decision

1. The project is a SwiftPM package. `./build.sh` is the only thing that assembles `MenuCal.app`,
   locally and in CI.
2. The suite is an executable target, `MenuCalTests`, with a small assertion harness. It is run by
   `./run-tests.sh` and exits non-zero on any failure.
3. View state lives in `@Observable` models owned by AppKit controllers. No `@State` anywhere.
4. Localisation uses `.lproj/Localizable.strings`, copied into the bundle by `build.sh`.

## Alternatives rejected

- **Install Xcode and follow the brief literally.** It would work, but every contributor and the
  CI would need it for a menu bar utility of a few thousand lines, and the release pipeline that
  already exists is built around SwiftPM.
- **XcodeGen manifest kept beside the package.** Two build descriptions drift apart; the purpose
  of B-1, no `.xcodeproj` merge conflicts, is met better by having no `.xcodeproj` at all.

## Consequences

- Code coverage (acceptance criterion 3) cannot be measured with `swift test --enable-code-coverage`.
  It is measured by building the test executable with `-profile-coverage-mapping` and reading the
  report with `llvm-cov`, see `run-tests.sh --coverage`.
- Snapshot tests render views through `NSHostingView` in the test executable rather than through
  an XCTest snapshot library.
- Third party packages that use `#Preview` or `@State` internally will not build here. Each
  dependency is probed before it is adopted.
